1. ENTENDA AS PEÇAS
VPS: computador alugado que fica ligado na internet.
Ubuntu: sistema operacional desse computador.
Docker: executa cada aplicação em um ambiente separado, chamado container.
Compose: arquivo que descreve os containers e suas configurações.
Node.js: executa o seu back-end. O PetCore leva o Node dentro da imagem Docker.
PostgreSQL: guarda os registros; o banco ativo do PetCore está na própria VPS.
Versity Gateway: fornece o armazenamento privado de fotos e backups do PetCore.
Caddy: recebe os acessos aos domínios e os encaminha para a aplicação certa.
DNS: aponta um nome, como petcore.tigertech.dev.br, para o IP da VPS.
HTTPS: protege a conexão do navegador com o sistema usando um certificado.
Deploy: instalar uma revisão conferida da aplicação e verificar seu uso real.

8. ESTRUTURA DE UM PROJETO NOVO
Prepare no próprio projeto: Dockerfile, .dockerignore, package-lock.json,
comandos de build/start, arquivos Compose, configuração do proxy e .env.example.
O .env.example documenta nomes de variáveis, sem segredos reais.
Para um projeto Node, confira engines e scripts do package.json; a versão do
Node da imagem deve ser compatível com aquele projeto. PetCore usa Node 22.
Front-end Vite deve ser compilado; o servidor de desenvolvimento não é produção.
No PetCore, a imagem reúne o back-end e os arquivos já compilados do front-end.
Se outro projeto ainda não tiver Dockerfile/Compose, peça a adaptação a partir
do package.json e da estrutura real dele: o comando start e as pastas de saída
variam. Não copie o Dockerfile do PetCore para qualquer projeto sem essa revisão.
Inclua os arquivos de implantação na revisão que será usada ou transfira apenas
os arquivos operacionais revisados, registrando sua origem e integridade.
No PetCore atual, deploy/ não existia naquele commit: os arquivos revisados de
implantação foram copiados separadamente e conferidos por hash.

10. CONFIGURAR O BANCO E OS SEGREDOS
Um projeto Node pode usar banco externo ou banco privado na VPS. A opção atual
do PetCore é PostgreSQL na própria VPS, sem depender de Neon ou Railway.
Para outro projeto, crie banco e usuário próprios e mantenha TLS e verificação
do certificado; não reutilize o usuário ou a senha do PetCore.
Para SaaS diferentes, separe bancos/usuários e credenciais com acesso necessário.
Dentro do PetCore, as empresas são separadas pelas permissões e pelo tenant;
não é necessário criar outro PetCore para cada pet shop.
Migrations e backups devem usar a conexão direta prevista pelo projeto.
O banco ativo do PetCore é petcore; a aplicação usa petcore_runtime com senha própria.
Não copie a conexão administrativa para a configuração da aplicação. A conta de
migrations e a conta administrativa ficam separadas, com arquivos privados.
Nunca conceda administração do PostgreSQL a uma aplicação para contornar um erro.
Guarde variáveis privadas em arquivos protegidos, fora do Git e da imagem.
Exemplo de preparação de uma pasta privada nova, na raiz do projeto:
    umask 077
    install -d -m 0700 deploy/private
Edite os arquivos privadamente. Se usar nano: Ctrl+O salva; Enter confirma;
Ctrl+X sai. Não exiba esses arquivos em capturas ou mensagens.

11. VARIÁVEIS DO PETCORE: COMO PREENCHER
Consulte .env.example e deploy/README.md para o catálogo; os nomes a seguir
descrevem a separação necessária, não um comando para substituir o deploy ativo.
Aplicação: banco limitado, DATABASE_SSL, CA autorizada, SESSION_SECRET, APP_ORIGIN
e serviços aprovados. Migrations: conexão de esquema própria ao mesmo banco/TLS.
Manutenção, lembretes e backup: configurações privadas separadas por função.
Na implantação atual, o processo carrega a configuração própria de um volume
privado. O Gerenciador Docker também referencia volumes persistentes e redes
externas. Não apague esses volumes nem gere um Compose só com o app e o proxy.
SESSION_SECRET precisa de pelo menos 40 caracteres aleatórios; não use exemplo.
APP_ORIGIN deve ser exatamente a origem HTTPS, por exemplo:
    APP_ORIGIN=https://petcore.tigertech.dev.br
PETCORE_HOST, no arquivo de seleção do Compose, recebe só o hostname:
    PETCORE_HOST=petcore.tigertech.dev.br
Os arquivos privados do PetCore usam format: raw, que exige Compose >= 2.30.
Neles, use NOME=valor, uma variável por linha, sem export, aspas externas ou
comentário depois do valor. O arquivo .env de seleção tem formato normal.
Não copie caminhos Windows de pg_dump/pg_restore: a imagem fornece os clientes Linux.

No PetCore, o controle confere arquivos/checksums e aplica apenas o que falta.
Execute uma vez por revisão necessária; não inicie o app se a migration falhar.

O DNS deve apontar para a VPS e TCP 80/443 precisam estar acessíveis.

O titular precisa autorizar a emissão e aceitar os termos da certificadora.
No PetCore, isso já foi autorizado para o subdomínio de testes e a Let's Encrypt.
Confira o domínio, emissor, validade e ausência de alertas no navegador.

noindex/nofollow pede que buscadores não indexem a homologação; não é senha.
Teste login, sair/entrar, permissões, cadastros e agendamento em computador/celular.
Teste recuperação de senha, fotos e exportações depois de configurar esses serviços.
Um 200 na saúde não substitui esses fluxos. Não contorne alertas de certificado.
O firewall atual não libera UDP 443: HTTP/1.1 e HTTP/2 funcionam; HTTP/3 fica limitado.

16. COMO FUNCIONAM OS E-MAILS AUTOMÁTICOS DEPOIS DA MUDANÇA
A VPS hospeda a aplicação; ela não fornece automaticamente o envio do PetCore.
O PetCore da Hostinger usa o Resend; a configuração foi preservada privadamente.
Avisos de suporte foram habilitados depois de conferir a fila vazia. O agendador
de lembretes executou com sucesso em 20/11 às 16h30, somente para tutores com opt-in.
Sucesso do job não significa que houve mensagem devida ou entrega na caixa de entrada.
Contratos de privacidade continuam aguardando respostas; a implantação não os aprova.
Preserve e confira SPF, DKIM e DMARC no DNS do remetente.
Um status Verified antigo do provedor não comprova que o registro DNS continua
publicado hoje. Confira os registros públicos antes de liberar os envios novos.
O código atual usa EMAIL_PROVIDER, EMAIL_API_KEY e EMAIL_FROM para recuperação
e avisos de suporte. Lembretes têm RESEND_API_KEY e RESEND_FROM_EMAIL separados.
Consulte os nomes reais em .env.example; não renomeie variáveis por tentativa.
Outro SMTP/provedor não está automaticamente implementado só por existir na VPS.
Faça um envio autorizado e teste abrir/consumir o link de recuperação no domínio final.
Confira recebimento e spam; “aceito pelo provedor” não garante Caixa de Entrada.
Desative os workers antigos antes de ativar os novos. Lembretes somente com opt-in.
Não deixe Railway e Hostinger enviarem a mesma fila em paralelo.

17. VÁRIOS SITES E SAAS NA MESMA VPS
Cada aplicação terá pasta, container, variáveis, banco/acesso e volumes próprios.
Exemplos de nomes de pastas: tigertech, nacao-animal, petcore, barbearia e salao.
Um único proxy deve receber 80/443 e decidir o destino pelo domínio.
Hoje o proxy do PetCore de testes já ocupa essas portas: não inicie outro ali.
Em uma VPS NOVA e vazia, pode-se planejar um proxy compartilhado separado,
com uma rede Docker externa, por exemplo tigertech-web, e aliases exclusivos.
Nesse plano de servidor novo, a rede é criada uma vez:
    docker network create tigertech-web
Os Compose participantes declaram essa rede como external: true.
Cada app participa dessa rede; seu Compose publica só a porta interna via expose.
O proxy participa da mesma rede e encaminha para o alias/porta daquele app.
Exemplo conceitual de blocos do Caddy, usando domínios que o titular controla:
    site-do-cliente.com.br {
        reverse_proxy site-cliente:3000
    }
    petcore.tigertech.dev.br {
        reverse_proxy petcore-app:4000
    }
Os aliases são exemplos, não a rede/nomes já instalados. Não copie esses blocos
sobre a configuração atual. A transição para proxy compartilhado exige preservar
os volumes/certificados, revisar as redes e planejar a troca das portas.
Não publique PostgreSQL 5432, Node 4000 ou a API do Docker na internet.
Projetos separados ainda disputam CPU/RAM/disco; acompanhe o consumo e dimensione.
Cada cliente deve ter acesso só ao que administra, sem receber a senha root geral.

18. BACKUPS E RECUPERAÇÃO
Mantenha backup do banco, dos arquivos/fotos e das configurações necessárias.
Uma cópia semanal da VPS não substitui o backup consistente do banco e dos objetos.
O banco PostgreSQL e o storage Versity atuais estão na própria VPS: uma perda
do servidor pode atingir dados e backups locais ao mesmo tempo. Mantenha também
cópia cifrada fora da VPS, com chave protegida em local recuperável.
No PetCore, fotos e backups usam destinos privados distintos e cópias cifradas.
Guarde as chaves de cifra, suas versões e a assinatura Android fora da VPS/bucket,
em local privado recuperável. Sem a chave correta, a cópia cifrada não é suficiente.
Ensaie restauração em banco/bucket novos e vazios; confira quantidades e arquivos.
Não restaure uma cópia sobre o ambiente ativo para descobrir se ela funciona.
Registre data, versão, resultado e responsável pelo teste. Use docs/PHOTO-RECOVERY.md.

23. APÊNDICE PRÁTICO: OUTRO PROJETO NODE, COMEÇANDO SEM DOCKER
Use este exemplo na pasta de um NOVO projeto, não na pasta do PetCore.
Premissas: package.json e package-lock.json na raiz, scripts build e start
funcionando, servidor HTTP na porta PORT=4000, ouvindo em 0.0.0.0, e rota
/health que retorna 200. Esse caminho precisa ser adaptado se sua API usa outro.
O script start deve iniciar o servidor compilado, não o servidor de desenvolvimento.
Preserve os scripts do projeto: confira-os com o responsável pelo código.
Monorepos, Next.js, bibliotecas nativas e outros formatos exigem adaptação;
o Dockerfile abaixo não substitui a análise da estrutura/saída daquele projeto.

Crie .dockerignore com este conteúdo mínimo, retirando os espaços antes dos nomes:
    node_modules
    .git
    .env
    .env.*
    **/.env
    **/.env.*
    private
    deploy/private
    .android-signing
    .aws
    **/*.key
    **/*.pem
    **/*.jks
    **/*.keystore
    **/*.p12
    **/*.pfx
    **/*.apk
    **/*.aab
    **/*.dump
    **/*.enc
    dist
    coverage
    *.log
    backups

Crie Dockerfile com este conteúdo; as linhas não levam espaços à esquerda:
    FROM node:22-bookworm-slim AS build
    WORKDIR /app
    COPY package*.json ./
    RUN npm ci
    COPY . .
    RUN npm run build && npm prune --omit=dev
    FROM node:22-bookworm-slim
    ENV NODE_ENV=production PORT=4000
    WORKDIR /app
    COPY --from=build --chown=node:node /app /app
    USER node
    EXPOSE 4000
    HEALTHCHECK --interval=30s --timeout=5s CMD node -e "fetch('http://127.0.0.1:4000/health',{signal:AbortSignal.timeout(3000)}).then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
    CMD ["npm","run","start"]

Crie compose.yml. Neste YAML, preserve a indentação relativa mostrada:
    services:
      app:
        build: .
        image: exemplo-node:teste
        init: true
        restart: unless-stopped
        read_only: true
        tmpfs:
          - /tmp:rw,nosuid,nodev,size=64m,mode=1777
        security_opt:
          - no-new-privileges:true
        cap_drop:
          - ALL
        env_file:
          - path: ./private/app.env
            format: raw
        environment:
          NODE_ENV: production
          PORT: "4000"
        ports:
          - "127.0.0.1:14001:4000"
Esse app terá acesso de teste SOMENTE pelo próprio servidor em 127.0.0.1:14001.
Ele não disputa 80/443 nem expõe Node na internet. Use outra porta local se ocupada.
Persistência de arquivos exige volume/bucket apropriado; este exemplo não o cria.
Para outro app, troque exemplo-node no nome da imagem e nos comandos -p, além
da porta local e do alias exemplo-app. Cada projeto deve ter identificadores próprios.

Na raiz desse projeto novo, prepare e edite a configuração privadamente:
    umask 077
    install -d -m 0700 private
    nano private/app.env
Preencha as variáveis exigidas pelo .env.example do seu app, usando banco de testes
e segredos próprios; salve o arquivo. As regras de format: raw da seção 11 valem aqui.
Não use as credenciais de outro SaaS nem habilite envio real durante esse ensaio.
Confira, construa, inicie e teste, um comando de cada vez:
    docker compose -p exemplo-node -f compose.yml config --quiet
    docker compose -p exemplo-node -f compose.yml build app
    docker compose -p exemplo-node -f compose.yml up -d app
    docker compose -p exemplo-node -f compose.yml ps
    curl --fail --show-error http://127.0.0.1:14001/health
Espere resposta 200 da sua rota e estado healthy. Leia logs se houver erro.
Esse teste HTTP local não comprova login com cookies seguros: teste-o depois em HTTPS.
Para pausar apenas esse exemplo sem apagar seus dados/configuração:
    docker compose -p exemplo-node -f compose.yml stop app

PARA PUBLICAR ESSE OUTRO PROJETO, REAPROVEITE O PROXY EXISTENTE
Primeiro planeje/aprove uma rede Docker compartilhada e conecte nela o proxy e
o app pelos respectivos arquivos Compose, de modo persistente após recriações.
Não basta uma conexão manual temporária; a rede precisa existir antes do deploy.
O nome tigertech-web é uma sugestão, não uma rede já configurada nesta VPS.
Exemplo de arquivo adicional compose.web.yml; substitua o nome da rede aprovada:
    services:
      app:
        networks:
          web:
            aliases:
              - exemplo-app
    networks:
      web:
        external: true
        name: NOME_DA_REDE_COMPARTILHADA_APROVADA
Somente após essa preparação, reaplique o app incluindo os dois arquivos:
    docker compose -p exemplo-node -f compose.yml -f compose.web.yml up -d app
Adicione ao Caddy EXISTENTE um bloco para um subdomínio autorizado, por exemplo:
    outro-projeto.tigertech.dev.br {
        tls tigertechbr@outlook.com {
            ca https://acme-v02.api.letsencrypt.org/directory
        }
        reverse_proxy exemplo-app:4000
    }
O alias exemplo-app deve ser exclusivo e acessível ao proxy na mesma rede.
Configure o DNS A desse subdomínio, obtenha autorização para o certificado e
valide/recarregue a configuração do proxy existente. Não inicie um segundo proxy.
Teste HTTPS, login e fluxos reais; só então programe a entrada em produção.
